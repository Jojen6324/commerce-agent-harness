# A/C 共享执行层修复（2026-10-20）

## 根因与改动

- 原先完成检查和 C 委派策略分别维护证据需求词表：同一请求可能在收尾时要求政策证据，预先却没有识别查证需求。`app/harness/requirements.py` 统一请求约束；共享主 Runner 在执行前获得证据需求，C 依据同一约束选择专家。A 由主 Agent 完成查证，不启用委派。该模块不读取评测 ID、场景标签或预期答案，不规定工具调用顺序。
- 原补救提示同时要求查政策、准备业务提案和转人工，容易把缺证据误修复为办理操作。改为按真实缺陷给出反馈。完成检查和输出校验共用最多两次修复额度，避免两套循环叠加。RAG 内部检索和自纠错逻辑未改写。
- 用户明确只咨询或禁止操作时，共享 ToolExecutor 在生成提案前拒绝业务写工具；明确要求查看待确认方案仍沿用原审批流程。Schema、身份、归属、预算和确认检查继续经过原执行器。
- 历史已核实商品属性原先只出现在上下文文本，未作为可追溯观察进入校验，专家可能复述事实却被判缺证据。A/C 共用服务器已核实的商品快照投影，保留原工具来源；订单、物流和退款状态不复用历史值。C 专家的继承观察来自服务器 ContextVar，不能从模型填写的 DelegateInput.context 获得证据权限。
- 无法访问订单的共用拒绝答复同时说明访问权限与订单号检查，避免将受限订单一律描述成订单号错误；不泄露订单存在性或归属。
